# Trusted local demonstration boundaries

The model/tool boundary cannot create approval or choose launcher identity. Java's fixed local principals distinguish proposer, manager, executor, and a fixture operator. These are application roles on a trusted local computer. A machine owner can edit launcher code or store files; this project does not prevent that, authenticate human identities, or provide a multi-tenant boundary.

Only two opportunity fields can be edited by proposals. Changing an opportunity version after review invalidates approval; evidence/account revisions and policy version are also checked. Evidence requires exact linked note revision, line ID, quote, and SHA-256. Exact provenance cannot establish semantic truth: a date in a sentence could be a meeting date, and text could be misleading. Human review and later independent semantic labels remain necessary.

The default authored script/rules have no external model/network path. Retrieved notes are data and never launch commands. The controller has no general filesystem, URL, SQL, or shell tool. Python's subprocess uses a fixed argument array and only an owned Java process; that process is not hostile-code isolation. Optional HTTP source accepts only literal loopback, disables proxies/redirects, and requires explicit live-model opt-in. A local service could itself use cloud-backed models; any future real run requires a user-authorized already installed local model. No such run has occurred.

The synthetic fixture operator can change records, note revisions/links/visibility, account scope, local role enablement, approval expiry or policy version for tests. These operations are absent from provider tools and require a synthetic store. Linked evidence revisions increment for changed, added or relinked notes. Cached stage results recheck evidence visibility; all operation/query paths recheck caller enablement and opportunity scope. Before a new apply, the approving manager must still be enabled. M1 stores without explicit access entries retain their original fixed roles. Demo scripted approval requires the explicit demo command and flag, creates a fresh synthetic fixture, and is visibly recorded as scripted review.

Atomic rename capability is probed at initialization. A failure is rejected rather than falling back to an unsafe copy. M1 file locking and atomic snapshot behavior were exercised on this machine. M2 commit failpoints are fixed launcher options available only on synthetic mutations, absent from provider arguments. They terminate only their own JVM before or after rename. The lock-holder helper is an eight-second owned test process. Worker M2 execution passed crash-injection, access-revocation, simultaneous delivery and corrupt-store tests. Captured actual JVM exits 71/72 and committed snapshots show one receipt/apply event after recovery with the original key. Power-loss/network-filesystem guarantees remain unverified.

M3 verification is separate from the acting provider and anchors fixture identity, exact case/repetition membership, immutable collections, original reviewed action, latest committed generation and pre-review semantics. File hashes detect byte changes; rehashed domain corruption also fails fixture/receipt/semantic checks. A machine owner who can replace code, frozen labels and all evidence is outside this demonstration's trust boundary. Reports/controls do not provide cryptographic attestation or enterprise authentication. A label-aware synthetic reviewer makes safe final state possible even when a proposal is wrong, so acceptance separately requires every rule-provider pre-review outcome. The pinned future CI job has read-only repository permission, standard runners, one matrix job at a time and no model credentials or publishing step; no hosted run has occurred.

Checkpoint save success must not be inferred from a committed CRM effect. On an exhausted replacement denial, the old checkpoint retains its original pending key and resume must query the authoritative operation result. A bounded retry does not prove a denial transient or diagnose its source. Owned Windows sharing tests deliberately exercise denial/release and committed-effect recovery; they remain unexecuted for authored-v6. No target deletion, in-place fallback, new approval or replacement action key is allowed. See `checkpoint-recovery.md`.
