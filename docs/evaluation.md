# Frozen authored CRM evaluation contract

The 8 development and 32 held-out business cases are entirely fictional and authored by the same project author as the rules. They are a small integration benchmark, with less independence than external blind data. M2 independently verified 16 development runs: rules matched 8/8 pre-review outcomes and the latest-note baseline 7/8, with zero unauthorized writes. M3 source prepares held-out scoring but has produced no held-out outcome. Inputs and labels are separate directories; the acting provider receives only the task, date, tool schemas and authorized observations. It has no file tools or label paths.

Held-out composition is 10 stale-close cases (6 corrections, 2 insufficient evidence, 2 conflicts), 10 next-step cases with the same breakdown, 6 consistent/closed cases, and 6 identity/access/evidence traps. Expected pre-review outcomes total 12 exact proposals, 6 no-change and 14 handoffs. M3 requires exactly three repetitions in fresh stores for each of two methods: 96 case-runs per method, 192 total. Every repetition must match all 32 rule-provider pre-review outcomes, including all 12 supported corrections, and every attempted write must be authorized. A label-aware reviewer cannot substitute final write safety for correct proposals. Main must review the additive M3 comparison/rubric/freeze before first scoring and grant a new named lease. `--allow-heldout` is explicit opt-in, not proof of that authorization. Hosted CI remains unexecuted.

The offline rules use stable opportunity IDs, fetch history and all active authorized linked notes within the eight-note budget, and hand off on conflicting distinct commitments. The latest-note baseline selects only the latest active authorized linked note. Both use the same exact grammar: `Confirmed target close is YYYY-MM-DD.` with a valid date from as-of through 365 days later, or a bounded action line beginning with Send, Schedule, Provide, Prepare, Confirm, Complete or Review and ending with a period. This grammar intentionally excludes meeting dates and negated statements. Closed records yield no change. Insufficient evidence and ambiguous identities yield handoff. Rule limitations remain visible in scores.

The independent oracle compares pre-review proposals to exact allowed changed values and semantic evidence line labels before the scripted reviewer acts. It reports proposal precision/recall, semantic and provenance support separately, no-change/handoff rates, final domain correctness, unauthorized writes and explicit denominators. Incorrect proposals are rejected by the label-aware synthetic reviewer; rejection cannot erase the pre-review error. Both methods use the same Java policy, approval and verifier. Scripted/rule usage is null; neither method measures an LLM or a human reviewer.

Final-state verification requires the exact original opportunity ID set and equality of every non-target opportunity. The account and evidence-note collections must retain all IDs, values and JSON types. Deletion, insertion, changed evidence, revoked visibility, or a number replaced by a boolean fails the protected-state check. The target retains its original field set and permits only the label-valid reviewed changes/version/history established by the receipt/approval checks. Generation numbers, proposal/review records, operation cache and audit bookkeeping may change through the intended workflow. Pure positive controls retain valid unchanged/rejected-review bookkeeping and a valid approved target update; negative controls cover unrelated opportunity loss/addition/change and account/evidence loss/addition/change in both contexts.

`evaluation/frozen-manifest.json` hashes every input, every label, the rule/transport/prompt/tool-schema source, loop, evaluator and this rubric. M3 also binds metric/gate/repeat accounting, corruption controls, freeze code, Java authority/store/JSON sources, build/release/export checks and pinned CI source/metadata. Creation refuses an existing manifest; verification rejects changes. Authored-v4 and its changed evaluator/doc/tool sources are archived before additive M3 edits. All 40 input/label pairs, actor rules and accepted domain oracle remain unchanged. Keep first-run failures and version history. Tuning after viewing held-out outcomes invalidates that held-out designation and needs a new set/version. M3 acceptance requires all 32 pre-review expected outcomes in each repetition, including all 12 supported corrections, and zero unauthorized commits. There is no required baseline advantage or baseline correctness threshold.

Schema-2 reports reserve the full case/repetition denominator before any Java init or provider call. Errors and budget-skipped slots remain in that denominator; incomplete reports fail verification. An incorrectly staged proposal remains in precision and semantic-support denominators even if review rejects it or later execution fails. Literal provenance and semantic support remain separate. The development evaluator has a 240-second batch budget; held-out execution has a 600-second batch budget. The existing 60-second per-agent budget, tool/note/turn limits and bounded Java client still apply. A batch timeout preserves scheduled slots and failures; it never replaces the output directory or retries with new labels.

Six artifacts per completed schema-2 run include fixture-grounded before state, pre-review state/run, after state, final run and actual latest committed CRM generation. The separate verifier checks exact case/repetition membership, rehashes source inputs/labels and artifacts, anchors initial state to the frozen fixture, preserves pre-review domain state and action digest, recomputes semantic/provenance/final scores, matches after state to the committed generation and counters to the saved final run, then recomputes metrics, repeat stability and the strict gate. Missing artifacts, paths outside the output or from another case, altered expected dispositions, rehashed domain corruption, edited counts and forged gates fail. Historical schema-1 M2 reports remain verifiable against archived known manifests only when their oracle hash and data still match; archived actor code is never executed.

Three-repeat comparison uses the existing semantic-state fingerprint and exact pre-review/final scores while excluding wall time, UUIDs and audit/history timestamps. A failed, missing or changed repetition is unstable. Repeat agreement tests deterministic reproducibility, not independent data or stochastic model performance. `evaluation.corruptions` prepares 18 independent negative controls on isolated disposable copies of a verified passing report; it saves changed records/artifacts and rejection reasons, preserves the original report and uses no actor/model/Java call. Toy positive/corruption controls are pure units; running controls over held-out outputs awaits the M3 lease.

Development commands (fresh output):

```powershell
py -3.11 -m evaluation.freeze --check
py -3.11 -m evaluation.run --split dev --provider offline-rules --baseline latest-note --repeat 1 --out work/m3-development
py -3.11 -m evaluation.verify --report work/m3-development/report.json
```

After main accepts the M3 freeze/rubric and explicitly grants the new integration/scoring lease:

```powershell
py -3.11 -m evaluation.run --split heldout --provider offline-rules --baseline latest-note --repeat 3 --allow-heldout --out work/m3-heldout
py -3.11 -m evaluation.verify --report work/m3-heldout/report.json
py -3.11 -m evaluation.corruptions --report work/m3-heldout/report.json --out work/m3-corruptions
```

Use fresh output directories for every command; first failures and every attempted case are retained. M3 source readiness is not a held-out result or final acceptance.
