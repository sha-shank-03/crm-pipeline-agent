# CRM architecture

Python owns a `Provider.next(messages, tool_schemas, limits)` interface. The M1 ScriptedProvider responds to tool observations from one authored CRM fixture. It selects pipeline, opportunity/history, note metadata, note text, and proposal staging in five turns. It is deterministic script behavior and provides no live model evidence.

The dispatcher validates exact argument names/types and exposes five tools. Java receives principal, as-of date, and store path as fixed launcher configuration, separate from provider arguments. `approve`, `apply`, and the synthetic fixture-edit operation are absent from the provider's tool set.

Java checks evidence provenance and structural constraints at staging, approval, and apply. Each proposal has a canonical immutable `action` object and a Java-computed SHA-256 digest. Proposal status is stored separately. Canonical action keys are recursively sorted; changes/citations are sorted by field; numbers are integers. Strings are UTF-8 without HTML escaping; explicit JSON nulls are preserved. Approval binds digest, manager scope, and 15-minute expiry.

Every mutation has a request ID and a fingerprint of operation, principal, as-of date, and arguments. The operation cache is part of the committed snapshot. Identical successful delivery returns its original result without creating a new generation. Different content under the same key is rejected. A proposal cannot be applied under a second key. Caller scope is rechecked before returning a cached result.

The controller writes exact stage/apply intent to `run.json` before the Java call. M2 resume first queries `operation_result` with the saved key/arguments and only retries if no commit exists. Operator review actions save their own immutable intent before approve/reject. An interrupted process is treated as unknown outcome until reconciliation. A stale/expired proposal terminates and requires a fresh reviewed proposal.

Store generations are JSON files named with a six-digit sequence. Every request holds an exclusive lock on a separate `store.lock`. The newest committed generation is validated, then the whole next state is written/flushed to a same-directory temporary file and renamed atomically to a new filename. Temporary files are not commits. There is no separate HEAD or audit append. A corrupt newest committed generation fails closed. Snapshot limits include the total generated store footprint, with no compaction fallback.

Gson 2.14.0 performs JSON serialization, with its declared Error Prone annotations 2.48.0 dependency on both compile/runtime classpaths. Their exact published POM/parent closure, hashes, license texts, and absence of packaged notices are recorded in `dependency-audit.json`. No Maven, JUnit, Error Prone compiler/checker, or model library is required.

M3 adds only evaluation/release source. The runner reserves both methods' complete case/repetition schedule before tool execution, saves pre-review evidence before label-aware review and records the actual committed generation separately from its copied after-state artifact. The verifier runs outside provider access, anchors initial state to frozen fixtures, reconstructs outcomes, checks counter/artifact/metric identities and enforces every rule-provider pre-review outcome. Cross-repeat comparison ignores timestamps/UUIDs while preserving domain outcomes; it measures deterministic reproducibility. Corruption controls use disposable copies and never execute an actor. Static release/source export has no Git/runtime dependency. M3 worker verification passed full regressions, all 192 held-out runs and repeats, report/control verification and the cached standalone clean-copy procedure.
